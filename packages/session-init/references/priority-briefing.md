# Prioritized working briefing

An explicit manual init prepares the user's working agenda, not only a rules acknowledgment. Comprehensive means all known items in the approved working scope are accounted for; it does not mean every company mailbox, repository or project was freshly audited.

## Recover, reconcile and establish coverage

Start with the existing full report/ledger, current conversation decisions, designated continuity store and actual worker/task receipts. Name the coverage denominator: the existing report plus each approved continuity/source set actually considered, and account for every known item or explicit omission/gap. Keep stable source/work IDs and deduplicate by canonical item, not title alone. Respect the user's explicitly completed, deferred or cancelled items; do not ask again merely because a source cache is old. If a provider still says open, record the user-confirmed outcome and source reconciliation gap separately rather than falsely editing source status.

Record each relevant source's scope, source update/as-of timestamp, fetched_at, last successful refresh and gaps; record generated_at for the briefing. Unknown timestamps remain unknown. Reading a cache now never makes its evidence current. Stale, missing, capped, inaccessible or unanswered sources make affected coverage partial. Preserve last-good evidence. Lack of response is not no-change or proof of completion.

Use only bounded authorized refreshes that can change the agenda or a consequential decision. ClickUp domain reads/synthesis go through its actual skill and AI contract after local hydration; native calls remain limited to permitted transport, audience checks and independent verification. Other sources follow their own skills and authority. Do not claim all connected accounts or projects covered without an explicit coverage record. No global startup audit or new source connection is implied.

## Item model and ordering

For each known item retain initiative, canonical source ID/link, owner, observed status/progress, exact user action/decision/question (or none), dependency/blocker, who is waiting on whom, waiting_since/age if evidenced, deadline/timezone if verified, can_finish_now and evidence needed next. Retain actual worker freshness, not an old “active” label. Unknown owner/age/deadline stays unknown.

Separate: needs the user now; delegated/in progress; waiting on others; deferred; newly completed/closed. Group the full report by project/initiative. Where GitHub mentions or assignments are in the approved scope, include unanswered questions/decisions with thread sources; do not equate assignment with an unanswered question.

Rank user-attention items by organizational impact and people unblocked, verified urgency/deadline and consequence, then known waiting age; prefer actions that can actually finish in the current call. A hard imminent deadline may override impact, with an explicit reason. Age is a factor, not an automatic override of impact. Do not invent scores, dates, hours saved or dependency counts. Explain ties/uncertainty briefly. Keep important computer-only or externally blocked work visible, but do not repeatedly offer it as finishable in the call.

Prepare the recommended first item's context: current ask, source-backed background, relevant prior decision, options if needed, actual consequence/trade-off, and the one question needed from the user. Do not turn proposals or historical claims into approvals. If no action is ready, state what is waiting and why rather than invent a decision.

## Written continuity and spoken delivery

Use the existing full report/ledger as a derived source-linked briefing. Resolve identity, current version, audience and update authority through the applicable artifact skill. Do not replace a narrow CEO priority cache with the broader report, create duplicate tasks, or silently adopt a different report. Stable derivative formats remain linked to the same canonical content. Private source IDs/locations belong in runtime bindings, not a public skill package.

Finalize one bounded update at the end of this manual preparation when already authorized and material content/coverage changed. Preserve source timestamps, human edits, stable IDs and version history; retain a baseline and use available version guards. Stop on conflicting drift. If supported concurrency protection is unavailable for a whole-body human-edited replacement, retain the last-good artifact and prepare a reviewable patch instead of blindly overwriting. Track canonical and derivative-format outcomes separately; one successful format is not success for all. No material change needs no new version. No current authority/destination or a failed/uncertain write leaves persistence pending, not a successful no-op; retain last-good content and state the exact gap. Reconcile uncertain effects before retrying only the unresolved write. This is not a recurring sync service or ongoing ClickUp progress publication.

The written briefing is comprehensive within its declared coverage; speech is concise. Open with the recommended order and why, then discuss only the first item. Give access to the full report through the current delivery rules when useful/requested. Do not recite internal rules or raw receipts. After a decision, preserve it in continuity and perform only authorized downstream steps. If independent background work takes time, switch to the next ready item and return significant results at a safe opportunity.

## Functional acceptance

Resource loading proves technical readiness only. Functional readiness requires a coverage-accounted briefing, reasoned priority order, prepared first-item context, and verified persistence when an update was due and authorized (or evidenced no-change or justified not-applicable). Overall invocation/full success additionally requires actual evidence of each applicable requested delivery gate; prepared or queued content alone cannot pass live voice acceptance. Record no-change with its evidence separately. Delivery is prepared/sent/spoken/heard only as actually observed. Missing optional data can yield a useful partial briefing, never a false comprehensive/current claim. Static fixtures, installed files and a repeated call on the same child do not prove fresh identity, cold-context recovery or live voice acceptance.
