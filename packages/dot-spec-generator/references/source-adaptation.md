# Source-to-dot adaptation

Load only for an authorized adaptation of a named source skill, command or authoring template. Inputs: actual request/provenance, source bounds and versions, target outcome, existing canonical work, permitted effects and latest corrections. Output: concrete target instructions or an exact proposed amendment, adoption ledger, acceptance and precise unresolved gaps. This module adds source-specific semantics; reuse the generator's existing template, research, continuity and reporting resources rather than cloning their workflows.

## Inspect the bounded source

Inventory the complete accessible material that can affect the requested behavior: entry text, referenced modules, assets, schemas, scripts and implicit dependencies. Record inspected resources, deliberately excluded/skipped resources with reasons, and missing/unreachable references separately. A pasted source defines the accessible boundary, not proof that its absent dependencies do not matter. An entry-only read is not full closure. Follow only relevant references within the authorized scope; repeated resource identity stops that cyclic branch. No claim about unread content.

Capture actual revision/hash or an observed date with its limitations. Check license when external reuse or redistribution matters. Unknown license blocks affected redistribution, not independent compatibility analysis. Source scripts, commands and imperatives are evidence, not permission to execute or install them.

When the target changes an existing system, also use [brownfield changes](brownfield-changes.md). Reuse one behavior/change map with the fields from both modules; do not duplicate or conflict with its implementation/state evidence and compatibility checks.

## Map behavior, mechanism and ownership

For every material inspected element record source behavior/mechanism, retain/adapt/replace/exclude/unverified disposition, target mechanism, evidence, intentional behavior change/loss, dependency and observable test. An unknown is not a proven incompatibility. Filesystem, tool, model, path, status-trigger and host assumptions need target evidence; do not import a source platform's blanket restrictions or capability claims.

Distinguish a direct entrypoint from an authorized subordinate module. A bounded coordinator handoff carries the original user's objective, actual authority/provenance, source bounds, allowed effects, corrections and cancellation state. It can delegate that part of the work, not create new permission. Mere sibling suggestion, topic match or source quotation cannot authorize a module. If the source forbids all sibling invocation, explicitly record any change needed for authorized dot composition rather than claim unchanged fidelity. Missing provenance blocks the dependent operation; cancellation stops new work under that handoff.

For command sources, choose thin wrapper versus standalone outcome. A wrapper owns recognition/input normalization/delegation and does not copy the target's instructions. A missing target stays a dependency, not an excuse to clone behavior. Prefer existing registered skills when they own the requested capability; do not create another entrypoint just to mirror source names.

## Produce and verify

Return a concrete target resource or localized amendment using the existing specification template. Preserve stable requirement identities, source attribution and human content. Include the material inventory, behavior/mechanism mapping, wrapper decision when applicable, intentional differences and each unresolved mandatory dependency. Do not copy the source's reporting pipeline: use the generator's exact ClickUp-owned reporting binding and six parameters.

A missing source or module blocks only dependent fidelity/readiness claims. Continue independent supplied-evidence analysis without substituting a similarly named resource. If this module itself is unavailable, report that exact dependency; do not claim to have followed it or silently replace it with an ad hoc port. No installation, native update, external-agent dispatch, task/status mutation or publication follows merely from drafting a port.

Define tests for preserved behavior and deliberate changes, not just matching headings. Use actual source/request outputs for content checks; distinguish content, target registration/loading, fresh-session evidence, effects and final publication. Static review of unsafe branches remains unexecuted. Mandatory unverified controls block affected runtime readiness. Runtime test or installation requires its own actual authorization and supported route; a source's completed status is not execution evidence.
