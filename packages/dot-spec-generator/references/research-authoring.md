# Research and authoring

Load for material research, source comparison or multi-part specification. Inputs: actual outcome, constraints, authorization, sources and selected rigor. Output: evidence-backed draft and explicit unresolved items. No external effects beyond current authority.

## Research boundary

Keep bounded supplied-evidence reconciliation and evidence-to-requirement authoring here. For a missing fact, check official sources first. For material authorized investigation, read [adaptive research handoff](adaptive-research-handoff.md), discover the actual sibling skill and pass its explicit depth/scope/effort contract; ask before unrequested deeper research. Do not substitute this module for an unavailable research skill.

State questions, source types, inclusion/exclusion rules and stopping condition. Prefer primary artifacts to summaries. Record source identity/version or fetched date/hash, observation scope and access gaps. Separate what a document claims from runtime observation. Preserve contrary evidence and source ownership.

Reuse existing owners when compatible. Classify each material source element: retain, adapt, replace, unsupported (affirmative evidence required), optional design choice, or unverified. Distinguish technical tool/auth/lifecycle dependencies from an author's preference for activation, hierarchy, fan-out or process ceremony. No generic skill becomes dot-native merely through a name.

If the user restricts examples to public OpenAI dot-branded sources, preserve that boundary. A paid listing or a claimed production-ready catalog is not source inspection or runtime validation. Do not use inaccessible internals as adopted behavior.

## Existing interface compatibility

When the output specifies the generator/ClickUp adapter boundary, load the bundled shared interface even for a design-only run. Cite `dot-authoring-delegation/v1` and map every required request/result category, operation allowlist, parent writer, per-effect state and cumulative budget/control semantics. Do not substitute similarly named prose or a new schema. Required prospective cap, attempt allowance, reply-read bound, verification/reporting reserve and persistent ledger may be explicitly unknown/no-send; unmeasured savings do not make safety-budget fields optional.

## Turn evidence into a contract

1. Outcome and measurable success; scope and non-goals.
2. Current baseline, existing owners, compatibility/reuse decisions and alternatives rejected with reasons.
3. Inputs/outputs, target substrate, capabilities, exact effect boundaries and unmet prerequisites.
4. Stable requirements: behavior, source/rationale, priority, dependencies, observable acceptance and failure/recovery.
5. Delivery order with explicit gates; no assumed deployment, schedules or agents.
6. Decisions, assumptions, questions and unexamined gaps, each linked to affected requirements and resolution evidence. Owner only if known.
7. Evidence/adoption ledger and current candidate version.

For an instructional package, distinguish entrypoint activation from authorized helper-module loading. Modules declare load condition, inputs, output, dependencies and permitted effects; detect cycles/missing references. A reference cannot authorize a sibling entrypoint or expand effects.

Tiny work may use one compact brief. Standard work exposes interfaces and reconciliation. High-risk work adds specific threat/failure and authority review; it is not merely a longer document. Record module selection and actual output size for comparison, but length is not a quality score.

## Acceptance

Before review: all material constraints mapped, no invented authority/owner/deadline, critical factual claims supported or explicitly unresolved, every requirement has an observable test, all requested effects individually verified or unresolved, no contradiction hidden in an average score. A candidate may contain blocked sections; it cannot call them implementation-ready.

Live validation uses actual requests/sources and genuine outputs. Content execution on captured real material is not installed-loader evidence. Unsafe negative branches may receive static review and remain unexercised; do not create harmful real failures to claim coverage. Known defects block affected use. A release may support only evidenced read/propose behavior, with all other scopes explicitly unverified.
