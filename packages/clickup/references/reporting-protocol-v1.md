# Shared reporting protocol — dot-reporting/1.0

**Authoritative contract:** `dot-reporting/1.0`. Load for generator reporting and when authoring any new skill specification. Inputs: actual authority, current run/evidence and scoped parameters. Output: local progress and a durable verified, pending, failed, uncertain or no-op reporting receipt. This is instructional guidance, not an executable hook, timer, permissions engine or atomic transaction.

## Single protocol and source access

The ClickUp skill's bundled resource `https://github.com/IronbellyOrg/irondots/blob/main/packages/clickup/references/reporting-protocol-v1.md` is authoritative. Discover and read the actual registered `clickup` entrypoint, then this resource and its linked request/result templates through supported skill reading with returned locators. Do not recursively invoke the generator or ClickUp entrypoint. Every newly authored skill specification must reference `dot-reporting/1.0` and this actual source identity, and define only **destination, target, payload, acceptance, privacy and access** parameters for its context. Destination/target identify the established canonical record and audience; payload includes the final history/artifact/status scope; acceptance identifies required effects and observable readback; privacy constrains disclosed content; access records permitted transport, capabilities, actual authority, single caller-owned writer and supported resource-read route.

Do not fork, silently copy or invent alternate reporting workflows. Specify how the consuming runtime will discover and read this exact registered ClickUp resource using supported skill/resource tooling; record observed access evidence, or mark access unverified/blocked. A local path, remembered text or link is not evidence that a different runtime can read it. Do not distribute copied protocol variants; inability to read the authoritative resource blocks dependent reporting until access is restored or an explicitly approved protocol revision supplies a supported route. Unsupported versions require explicit contract reconciliation, not guessed compatibility. Do not grant access or install dependencies merely to satisfy the reference.

This protocol is distinct from `dot-authoring-delegation/v1`. That Brain adapter remains read/propose-only with unchanged controls; general final publication is performed by the single authorized caller, never implicitly delegated to Brain.

## Fixed sequence

1. **Local progress ledger.** Stage progress, checkpoints, evidence and artifacts under the authorized workspace's `output/` directory, respecting a user-designated subfolder. Retain stable run/operation/artifact identity, source versions, decisions, partial/blocked state and completed/uncertain effects. No initial ClickUp task is required. No ongoing report/progress writes or progress polling. Read only bounded existing canonical context needed for material decisions; preserve its identity and human edits.
2. **Finalize evidence and payload.** On completion of the authorized work and reporting, consolidate the historical record, final artifacts/references and truthful final status. Check the six scoped parameters, original write authority, actual supported transport/capability evidence, privacy, destination, known notification/status-transition effects and existing canonical content. An unresolved critical publication condition leaves a local pending receipt, not an external write. Cancellation does not grant publication permission.
3. **One coordinated final batch.** The single authorized caller writes the finalized authorized payload to the established target, using the smallest supported effect set. A batch is one coordinated delivery and may require multiple bounded provider calls; it is not atomicity. Before each affected write perform only necessary scoped concurrency checks, preserve human changes, and stop on material drift. Do not create a task/list merely because work occurred. Track components individually; do not repeat already verified effects.
4. **Bounded readback.** Verify the requested effects using authoritative, targeted reads and actual remaining limits. A successful request alone is not readback. No blind duplicate retries: reconcile an uncertain outcome before retrying only the unresolved effect. Access/quota blocks and unobservable outcomes remain explicit; do not invent quotas, evade limits or poll indefinitely. Failed writeback does not replay completed research or authoring. Resume only the unresolved delivery/verification stage within current authority.
5. **Durable receipt.** Save the run/operation identities, protocol/source version, payload identity, target, actual effects, verification evidence and individual verified/pending/failed/uncertain states in the authorized local ledger; include canonical artifact references when observed. Record exact remaining gates and next permitted action. Do not report a partial batch as fully published.

## No-op and acceptance

Every new skill specification assesses this same contract. If direct ClickUp reporting is unnecessary or unauthorized (for example a purely conversational answer or a subskill returning to its authorized parent writer), state the justification in its scoped parameters: complete steps 1–2 proportionately where local artifacts are authorized, mark step 3 no-op, step 4 not applicable, and retain a proportionate receipt/result handoff in the authorized existing channel. Do not create files or tasks solely to satisfy ceremonial logging where that is outside authority. Missing authority or access for intended publication is pending/blocked, not a successful no-op.

Observable acceptance must cover the fixed sequence, no initial task dependency, no ongoing report writes, final-trigger correctness, source/version/read-route evidence, single writer and actual authority, minimal scoped effects/readback, deduplication and uncertain-outcome handling, partial receipts and no replay of completed work. Unsafe failure branches may be reviewed statically and must remain labeled unexecuted. No statement in a skill specification proves runtime enforcement or future tool availability.

## Reporting preparation and receipt normalization interface

The ClickUp skill owns this protocol and the exact [request template](../assets/reporting-request.md) and [result template](../assets/reporting-result.md). It prepares a local final reporting packet or normalizes actual coordinator receipts; it does not execute publication, send Brain messages or enable new mutation operations. The coordinator owns separately authorized transport and final publication. Do not substitute a Brain brief for a reporting packet.

Use `dot-reporting-request/1.0` and `dot-reporting-result/1.0`, each referencing `dot-reporting/1.0`. Read both templates before use. Validate every field, version, enum, correlation identity and scoped parameter; retain explicit unknown/null values with reasons, never fabricated capability or provider receipts. Reject unsupported versions, missing fields, mismatched identity, unverified publication authority or unverifiable transport for affected readiness. Return a structured blocked/partial result; independent local preparation may continue. `prepare` cannot report external completion. `normalize_receipt` consumes genuine evidence, not an instruction to send. Every effect stays separately verified, pending, failed, uncertain, not_run or not_applicable. A partial receipt cannot become a fully verified batch. This is an instruction-level schema, not runtime validation enforcement.
