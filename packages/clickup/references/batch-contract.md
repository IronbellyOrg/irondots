# Batch contract — dot-approved-batch/0.1
Load for all extension staging. Inputs are actual user scope and bounded source observations; outputs are local validated batches and handoffs. No connector effects.

ClickUp alone owns live state. The local document is a cache and proposal ledger. Preserve source payloads without deleting unknown fields. Separate observations, typed projections, relationships, proposals/actions, approvals, attempts, effect receipts, budgets, coverage checkpoints and handoffs. Every identity is an opaque string, never a display label. Preserve source_updated_at separately from fetched_at and generated_at; unknown timestamps remain null. A new fetch does not rejuvenate source evidence.

Use the bundled template and helper. Observation keys include provider/workspace/type/source ID; observation metadata records endpoint, principal reference, query, coverage, adapter version, privacy, errors and timestamps. Field states include value, explicit-null, empty, not-requested, not-returned, unsupported, inaccessible and parse-error. Relationships retain direction, type, source/target identities and resolved/unresolved/inaccessible evidence. Preserve raw attachment references without downloading binaries by default. Failed/partial reads retain last-good observations; absence never proves deletion.

Actions bind exact target, recipient evidence, payload, baseline, dependencies, preconditions, side effects and verification plan. Approval fingerprints cover all material action fields and batch scope revision. Store actual approval evidence/reference, not a boolean invented by the helper. Changes require a new version and approval, never editing history. Attempts and receipts are append-only; local IDs are not provider idempotency keys. A receipt is a claim until authoritative evidence is independently checked.

Select stdlib SQLite for the executable local ledger: BEGIN IMMEDIATE transactions, rollback journal, synchronous=FULL, bounded busy timeout, append-only snapshots/events and owner plus expected-revision checks on every save. The JSON envelope remains the portable interchange format. Restart/rollback/concurrent-CAS tests validate local behavior, not hardware disaster durability, cross-session/executor retention, distributed ownership or safe external replay. Use one approved store path per batch and record its executor; do not copy a live database and assume ownership transferred. Never put raw database/chat contents in shared Space. Do not enable writes from this release. Keep private raw captures out of shared final reports. Stage a redacted final synthesis separately under the existing reporting protocol, with explicit destination/audience checks.

## Executable interface
Run `python scripts/batch_stage.py validate --input <batch.json>` before import. Stage with `stage --input <batch.json> --db <private-output>/batch.sqlite --owner <coordinator-id> --revision <expected-revision>`; a new batch uses revision 0. Export with `export --db <store> --batch <batch-id>`. `readiness --input <batch.json> --action <id>` lists gates and always returns dispatch_ready=false in this release.

For programmatic preparation import `observation`, `field`, `conflicts`, `approve`, `consume`, `validate`, `readiness`, and `Store`. `approve` records a supplied genuine instruction reference; it cannot authenticate or manufacture user consent. Save combined attempt/budget or receipt/projection changes in one `Store.save` transaction. Save rejects stale revisions, other owners, edited immutable histories and replay/reversion of in-flight/verified actions. External SQL/file edits are outside these application guards. DB schema version 1 rejects unknown future versions. All source timestamps, unknowns and effect evidence are supplied from observations, not inferred by the database.

No automatic ownership takeover is implemented. A lost owner requires explicit coordinated recovery after checking pending external effects; copying the file or changing its owner string is not a recovery protocol. This conservative limitation is preferable to duplicate publication. Process-restart tests do not establish future executor retention.

Verified effects retain the frozen attempt's approval_id and approval_fingerprint plus unchanged material action hash. Later scope revisions invalidate remaining approvals without invalidating verified historical effects. This release does not automatically resolve an uncertain/executing attempt to failed or retryable: reconcile externally and obtain a separately reviewed recovery path rather than relabeling uncertainty.

## Consumer portability gate
Native resource reads may expose Markdown/JSON but not the Python script. Verify an actual authorized executor and materialized script with matching source hash before running it. An executor-less caller delegates to its authorized parent/verified execution context and consumes actual execution receipts; absent that route, keep preparation instructional and report executable staging blocked. Never infer a script path, durable database or completed transaction merely from installed skill availability.
