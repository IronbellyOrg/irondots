# Existing-task ledger reconciliation profile

Contract `dot-ledger-reconciliation/0.1`. Manual Session Init is the trigger; this is neither a service nor an extension to the existing task update schemas. Separate planning truth, local projection and actual effect receipts. The current user's approved initiative, identity, effect, audience and data boundaries govern; approval to reconcile does not assign new effect permissions.

## Batch read and exact write boundary

Hydrate existing continuity first. Use one bounded private Brain read/propose batch keyed to approved workspace/list/task IDs and minimal fields: current status/raw status options or gap, revision/source update, title, owner IDs, due date, priority, dependencies and remote terminal evidence. Include exact IDs that are now closed; no workspace-wide discovery or disclosure of local ledger contents. If continuation is needed, preserve denominator, unresolved IDs, cumulative budgets and prior results; independent readback must be linked to the actual response, not a remembered label. Assign a new unique invocation ID for each manual entry. Remote observations must belong to the invocation that initiated the source read, evidenced by the current read receipt; a cached result must not be relabeled. An unchanged revision fetched anew can qualify. A pending response at the cumulative wait limit is partial, not a reason to defer the available local briefing. A missing or changed remote mapping is unmatched/blocked; never infer completion from absence. No blind native domain fallback or widened search. Keep native ClickUp users unaffected.

ClickUp status and local status are compared with their **last verified common baseline**, never based on last-write timestamp alone. First agreement may establish a baseline once local observation/save is verified; disagreement without a baseline stays a conflict. If both sides change differently, hold both status effects. ClickUp-owned metadata (owner, date, priority, dependencies and title) may update a local projection only when its current field observation is verified, including verified null; keep independent private notes and commitments untouched. Do not push metadata. A no-op produces no remote write. A known terminal state requires evidence from this exact list and mapping; terminal success requires the accepted completion evidence applicable to that task.

An outbound status-only update remains prospective unless a supported existing exact route and typed capability evidence go with it. `dot-brain-execution/0.1` does not support task_update. `0.2` supports a different, explicitly authorized milestone description append with optional narrowly mapped status update; it is not permission to append a status-only reconciliation marker. Never misuse either. If a separately authorized status-only Brain operation is both supported and evidenced, retain its exact independent before/after, workspace/list/task, known triggers and allowed side effects, protected fields, approval, durable operation key and verification. Apply the execution reference's external-operation receipt route when the helper cannot represent that exact supported effect. Recheck live preconditions immediately before mutation and never dispatch without exact current and target values. Preserve closing/trigger guards; no calendar, task, agent or human side effects outside the approved transition. On timeout preserve uncertain state, use authoritative readback before considering any retry, and maintain the last confirmed baseline. Do not pretend ordinary read/propose grants push authority.

## Offline input and output

`ledger_reconcile.py` ships with Session Init. Supply a private JSON object with `contract_version`, `trigger=manual`, actual `invocation_id`, `scope_inventory_complete` (observed), and `items`. Each row has `item_id`, `in_approved_scope`, `link={workspace_id,list_id,task_id}`, `local_status`, optional `local_projection`, `uncertain_effect`, `remote`, `status_map`, and `baseline` (null if none). Remote and mapping repeat exact identity: remote contains matching `invocation_id` bound by the evidence pointer to the current independent read, raw `status`, string `revision`, `independently_verified`, evidence pointer, terminal_evidence_ref for newly observed done/cancelled, and optional fields `{known,value}` (only set known for verified observations); status map has `verified_for_list`, evidence pointer, raw→local `pull`, local→exact raw `push`. Baseline repeats identity, verified `status`, `raw_status`, and `receipt_ref`. Optional `authority` and `capability` repeat identity and bind exact `before`, `after`, `baseline_ref`, and separately inspected `evidence_ref`; authority flags are `explicit_user_status_decision,scope_current,transition_allowed, plus completion_evidence_ref for done`; capability flags are `independently_verified,effects_known,readback_supported`. Do not fabricate these values from a source comment or boolean alone; one coordinator verifies actual referenced evidence and confirmation scope. Local supported coarse states: `todo,in progress,done,cancelled`. Use exact observed ClickUp status names and avoid inferring semantics for unmapped statuses.

Output is `plan_only` with provisional coverage and row dispositions: `pull`, `push_candidate`, `bootstrap_candidate`, `converged`, `unchanged`, `conflict`, `blocked`, `unmatched`, `excluded`. ClickUp-owned metadata pull is independent of status unless identity/scope/evidence is bad. Never apply stale candidates or expose private rows externally. Plan coverage is not runtime success. For a compact execution receipt record invocation identity/scope/counts, affected IDs/fields, observed revisions/exact status and limited evidence pointers, verified baseline advancements, errors/uncertain effects and next permissible step. Keep raw tool receipts private and load only for a specific baseline/conflict/audit; do not retain all of them in prompt context. No schema change is implied for legacy execution/reporting.
