## Minimal request/result handoff
The task-list caller provides stable logical list ID, Space file ID, current milestone ID/kind, known canonical workspace/list/task IDs (or explicit authorized create scope), source revision/fetch times, approved semantic delta/acceptance evidence, destination audience/privacy and actual effect authority. The ClickUp coordinator resolves current canonical target/status through AI, preserves existing task/child/checklist IDs if already canonical, and uses exact execution envelopes—not a rival connector schema. Unknown audience/location blocks only remote work. Default one sibling task, not a new ClickUp List. IronFlow HUMAN planning for AI/skill work; CEO for other personal work; explicit project/privacy routing wins. These are routing rules, not guessed IDs.

Result uses the execution per-effect contract and durable registry read receipt: canonical IDs and mapping, operation/effect/payload IDs, actual source revision/update time/fetched_at, last successful sync, actual readback evidence, reported versus independently verified disposition, and next permitted action. Task-list checkpoint stores concise verified/pending/failed/uncertain/cancelled state plus local receipt reference. Raw private replies/debug logs do not enter the public/user artifact.

## Milestones and one final effect
1. Hydrate existing list mapping/operation locally first; zero provider calls merely to remember progress. Match stable identity, never title alone. Ambiguous match blocks creation. Consequential live writes recheck relevant current truth; fetched_at does not freshen old source evidence.
2. **Initial:** with explicit authority reuse existing sibling; if none, existing task_create under execution/0.1 or 0.2 establishes one sibling using observed destination/status and stable dedup key. Verify create and save IDs before any existing-target update; unknown create is reconciled, never duplicated. Existing canonical children are linked, not recreated. The initial AI-created body may already cover initial progress; do not append a redundant initial block.
3. **Material:** only meaningful phase completion, blocker/decision change or approved scope change qualifies. Do not emit every step/keystroke, unchanged payload, timer polls or automatic notifications. Use execution/0.2 task_update for compact AI-authored append and, only if proven/authorized, exact mapped status. No implied assignments/dates/dependency changes. ClickUp is source of shared fields; Space is readable plan/evidence/checkpoint. Human conflicts win over stale local proposals.
4. **Final:** only after required checks and required delivery are verified. One final task_update may include final history/artifact links and verified terminal mapping. That **same operation/effect/payload and receipt** is the opted-in caller's final reporting delivery: prepare/normalize dot-reporting-request/result/1.0 for that final scope using the actual final receipt, never send a second duplicate report_create/task/create/final write. Retain both protocol/profile identities and explicitly mark milestone opt-in; this is not a claim unmodified legacy consumers permit milestones. Underlying work completion and reporting/sibling closure remain separate. Missing required terminal status or mirror acceptance blocks overall completed/Done move, not preservation of good Space work.

## Conflict, partial, restart and cancellation
Keep stable logical list ↔ Space file ↔ ClickUp task/list mapping, including existing remote row IDs where present. Keep each milestone identity stable across retries and hash its approved payload; changed content under same identity is conflict, not replacement. New authorized material scope uses a new milestone linked to predecessor after unresolved effects reconcile. A single coordinator and registry own dispatch; do not bypass unresolved updates with another DB/key. No claim of distributed lock or provider CAS.

If Space saved but ClickUp failed, retain the good file and pending mirror checkpoint; resume only unresolved sync. If ClickUp succeeded but Space receipt/save failed, reconcile by task/operation/history and update the same Space identity without replaying ClickUp. Missing reply is unknown, not no change. Partial multi-effect outcomes remain per-effect, never overall success by inference. Preserve verified history through newer partial returns.

Cancelled list remains cancelled, not successful done or an automatic terminal-status transition; cancel future local dispatch and preserve uncertain remote outcomes. Remote cancellation requires actual supported effect/evidence and separate authority. Reopening requires user authority, same Space/ClickUp identities and new material milestone; no duplicate sibling. Semantic blocked/done/cancelled states do not invent destination status labels. Preserve owner/due/dependencies unless a future explicitly reviewed schema permits separate authorized changes; this version does not.
