# Opt-in execution — dot-brain-execution/0.2

Additive, explicit version. Load [execution/0.1](brain-execution-v0.1.md) for its unchanged envelope, four legacy effects, authority/audience/budget/continuity/reporting profile and result rules. The same fields and legacy effect validations apply to 0.2. **0.1 still rejects task_update.** No new database schema or dispatcher. `scripts/brain_state.py` uses the same registry and `scripts/task_progress.py` only validates local progress records/readbacks. Old consumers and persisted operations retain their original versions. Installed, loaded, tested and operational are distinct.

0.2 adds only the following `task_update` shape for [dot-task-list-progress/0.1](task-list-progress-v0.1.md). It does not enable arbitrary updates/checklists. One progress update per milestone operation; use `semantic_key = progress:<stable list_id>:<stable milestone_id>` in helper create. Existing operation with that key is hydrated, not recreated. A previous unresolved update to the same workspace/task prevents a later update even if its container moved; reconcile it first. A cancelled predecessor with zero recorded calls is the only never-dispatched exception. Target/readback changes require review, not a bypass through another key/store.

## Exact effect shape
Retain normal effect fields: effect_id, type, target_or_creation_rule, payload, baseline, authority_ref, depends_on, side_effects, verification, capability_state. `type=task_update`, `capability_state=bounded_supported` only after actual scoped readiness. Unknown capability is a local blocked proposal, not a sendable record.

- target_or_creation_rule: exact string `workspace_id`, `list_id`, `task_id` of the existing sibling.
- payload: `profile=dot-task-list-progress/0.1`, stable logical `list_id`, `space_file_id`, stable `milestone_id`, `milestone` (initial/material/final), `state` (backlog/in_progress/blocked/done/cancelled), nonempty `body_requirements` (AI authors substantive concise content), `payload_id`, `marker`, `status_change` (null unless separately enabled below).
- payload_id: canonical SHA256 via `task_progress.payload_identity(payload)`, excludes only payload_id/marker. marker: `task_progress.marker(payload, operation_id, effect_id)`, binds list+operation+effect+payload. Do not improvise serialization.
- baseline: `revision` (observed date_updated), full exact `description`, its UTF-8 `description_sha256`, `fields`, `evidence_ref`, `fetched_at`. Fields exactly name/status/assignees/due_date/start_date/priority/dependencies, including genuine null/empty values. Missing fields are unknown, never invented empty. Baseline must come from authorized pertinent live source observation, not old hydration presented as current.
- verification: exactly ai_authorship, complete_content, approved_destination, excluded_private_data, baseline_precondition, human_content_preserved, owned_marker, no_unapproved_fields, status_mapping.

AI must reread the exact target immediately before mutation and compare revision/full-description hash and all protected fields. Drift stops affected update for reconciliation. Append exactly `baseline.description + "\n\n" + marker + "\n" + AI-authored progress text`, text 1–3000 characters. Preserve the full original prefix; never replace prior sections. Exactly one marker; already present means reconcile, not append again. Same marker with different content is a conflict. Retain actual returned content hash so changed readback cannot masquerade as same receipt; repeated same-effect readback with changed content is conflict-invalid. Multiple historical blocks are bounded milestone history, not an endlessly growing per-step feed; compaction is not enabled.

The provider is **not claimed to support atomic compare-and-swap**: preflight and post-readback reduce/detect races but do not eliminate concurrent human edits. Detected drift remains conflict/partial; never auto-restore over a human change. Typed readback uses exact existing task and description, checks task/container, full preserved prefix/unique marker, revision and all protected fields. Missing fields/readback means unverified. Coordinator assessment additionally binds actual AI authorship, precondition observation, semantic content, evidence and authorized status mapping; a structurally valid local record is not permission or proof.

## Optional status change: prospective, fail closed
Default null preserves actual ClickUp status. Description semantic state does not imply a remote status transition. Non-null has exactly from/to/semantic_state/authority_ref/capability_evidence/acceptance_ref/target_terminal. `from` equals observed baseline status; `to` is an actually observed destination status, not an invented label; semantic_state equals payload state. target_terminal is observed boolean. Terminal success is allowed only for done with required acceptance passed; done cannot map to nonterminal. Blocked/cancelled do not map to terminal success. No owner/date/dependency/priority changes are permitted.

`capability_evidence={path,sha256}` binds a private retained JSON artifact, not an arbitrary nonempty reference. Required artifact values: schema `dot-status-capability-evidence/0.1`, evidence_class `actual`, independently_verified true, exact workspace_id/list_id/task_id, before_status/after_status matching this transition, target_terminal, authority_ref matching this authorization, operation_id, reply_id, verified_at, independent_readback_ref, before_ref, after_ref, reviewer. Retain underlying real receipts, genuine source times and independent readbacks. Revalidate the retained artifact again at send and selected continuation reservation. Helper hash/shape checks are coordinator attestations, **not authentication** or a substitute for reviewing underlying evidence. Synthetic fixtures cannot enable real dispatch. Evidence does not establish another target/transition. A prospective pilot lacking proof must remain an explicitly authorized external-operation receipt path under existing routing, independently verified before reuse; no manufactured helper mediation or circular claim of proven status support. This release makes no live status-capability claim.

## Compatibility and recovery
Use normal actual reply ingestion; only task_id is an allowed reported output. Reported does not mean verified. Reuse task_content typed readback and exact frozen checks in record-assessment. A local cancellation stops future dispatch; it does not prove remote cancellation. Missing replies/uncertain effects require authoritative reconciliation; only explicit proven non-dispatch under unchanged authority qualifies for existing bounded continuation. Never replay a verified milestone, task creation, report, or Space effect. Package rollback restores instruction behavior, not external state; preserve 0.2 receipts and do not open new 0.2 operations with old code. No migration of existing 0.1 data is required.
